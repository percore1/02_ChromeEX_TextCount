# TextCount — Web アプリ移行 設計メモ

Chrome 拡張機能 → Vercel デプロイの会員制 Web アプリへ移行するための設計。
（本ドキュメントは設計のみ。実装は未着手）

---

## 1. 実現の可否（結論：高い実現性あり）

現行コードを精査した結果、**コア機能の大半はそのまま移植可能**です。

| 機能 | Chrome依存 | Web移行 | 備考 |
|------|:---:|:---:|------|
| 文字数カウント（除外ルール） | なし | ◎ そのまま | `processPlainText` / `processHtml` は純JS文字列処理 |
| 校閲チェックエンジン | `chrome.runtime.getURL` のみ | ◎ ほぼそのまま | `proofreading.js` は純JS。JSON取得を `fetch('/data/...')` に変えるだけ |
| .docx 読み込み | なし | ◎ そのまま | `mammoth.browser.js` はブラウザ動作 |
| 全画面校閲ツール（review.*） | `chrome.storage` のみ | ◎ ほぼそのまま | テキスト受け渡しを state/URL に置換 |
| 貼り付け入力 | なし | ◎ そのまま | |
| ~~自動（ページ選択の検出）~~ | — | **✕ 廃止** | **本仕様では実装しない**（下記） |
| ページ内ハイライト/ジャンプ（他サイト） | — | ✕ 廃止 | エディタ内のジャンプは実装する |

**要点：** アプリの「頭脳」（カウント・校閲ロジック）は既に純JSで完成しており、移行リスクは小さい。

### 入力仕様の確定（重要・本指示で確定）
- **対象は「テキストボックスに貼り付け／入力した原稿」のみ。**
- 拡張機能版の「選択範囲をリアルタイム自動検出」は **実装せず削除**（content script / `chrome.tabs` / `chrome.scripting` 依存もすべて不要に）。
- これにより Web 移行の障害は実質ゼロ。Web完結で全機能を提供できる。
- ※将来オプションとして「選択テキストを送るだけの薄いコンパニオン拡張」は検討余地ありだが、現行スコープ外。

### 認証（会員ID発行制）
「アカウントを発行したユーザーだけ」= **招待制 / 管理者発行**。自己サインアップは無効化。

| 方式 | 向き | コスト | 推奨度 |
|------|------|--------|:---:|
| **Auth.js (NextAuth) + Vercel Postgres/Neon** | フルコントロール・発行制と相性良 | 無料枠で十分 | ◎ 第一候補 |
| Clerk（Vercel ネイティブ統合） | 最速で導入・招待制対応 | MAU課金 | ○ 速度優先なら |
| Supabase Auth | DB込み・招待制可 | 無料枠あり | ○ |

→ **Auth.js + Postgres** を推奨（発行制の細かい制御・将来の利用ログ/権限管理に強い）。

## 2. 開発方針

1. **ロジック資産を最大活用** — `proofreading.js` / カウント処理を TS モジュール（`/lib`）に移植。フレームワーク非依存なので**ほぼ無改変**。移行の核心リスクをここで潰す。
2. **クライアント完結の処理** — カウント・校閲・docx変換はすべてブラウザ内で実行。**原稿テキストはサーバーに送らない**＝サーバーコストほぼゼロ＋編集データのプライバシーという強い訴求。サーバーに乗るのは認証・会員情報のみ。
3. **フレームワーク** — Next.js（App Router）on Vercel。
4. **認証ゲート** — `middleware.ts` でツール画面を保護。未ログインは `/login` へ。会員は管理者が発行（招待制）。
5. **データ** — `text_checklist.json`（226件ルール）は当面 `/public/data` に同梱。将来は DB 化して管理画面から編集可能に。
6. **リポジトリ** — 拡張機能は `/extension` へ退避し、Web アプリを `/web`（または新規ルート）に。拡張版も当面は併存可能。

### 想定アーキテクチャ
```
web/
  app/
    (auth)/login/page.tsx        ← 会員ログイン
    (tool)/page.tsx              ← メインツール（要ログイン）
    api/auth/[...nextauth]/      ← Auth.js
    admin/                       ← 会員発行（管理者のみ）
  lib/
    counting.ts                  ← content.js / sidepanel.js から移植
    proofreading.ts              ← proofreading.js から移植（ほぼそのまま）
    docx.ts                      ← mammoth ラッパ
  public/data/text_checklist.json
  middleware.ts                  ← 認証ガード
  prisma/ or drizzle/            ← users テーブル
```

## 4. UI 刷新コンセプト（`design/ui-mockup.html` 参照）

**コンセプト：「朱入れ（しゅいれ）」** — 校閲＝赤ペンという編集文化をキーカラーに反映。
**※デザイン方針は本指示を最優先。元の MD / 要件定義と相違があれば本方針を優先する。**

- **配色（白・黒・朱の3色）** — 背景・各ブロックはすべて**白**。文字は真っ黒を避けた**やや薄いグレー（#262626 / 黒の濃淡で階層表現）**。アクセントは**朱色 `#D6402F`** のみ。
- **書体** — **メイリオ系ゴシックで統一**（可読性最優先）。`Meiryo, メイリオ, Hiragino Kaku Gothic ProN, Yu Gothic UI, Segoe UI`。明朝は使わない。
- **レイアウト（参考ツールを参考）** — 左：機能ナビ＋操作 ／ 中央：**白いテキストボックス**＋行番号＋インライン朱指摘 ／ 右：カウント結果＋カテゴリ別校閲カード。
- **入力** — **貼り付け／入力した原稿のみ**が対象（自動検出なし）。エディタは「テキストボックスと分かる白背景＋枠線＋フォーカスリング」。
- **(a) 使い勝手** — 巨大なライブ文字数、除外内訳・漢字比率を即時表示。指摘クリックで原文へジャンプ、カードの✕で個別非表示。
- **(b) 小気味よい動き** — 段階的フェードアップ、数字のカウントアップ＋pop、朱の下線が「描かれる」インクアニメ、文マーカーの滲み、カードのスライドイン、トグルのスライド。
- **(c) 初心者にも直感的** — 「貼る→数える→朱を入れる」の3ステップ案内、凡例、空状態プレースホルダ。

> ブラウザで `design/ui-mockup.html` を開くと、打鍵でカウント・漢字比率が動き、朱の下線が描かれます。

## 5. Phase 2 以降の検討事項（※今は未実装・方針メモのみ）

将来的に以下3機能を追加したい。**いずれも DB が必要**になるため、ここで土台の方針を固めておく。

### ① 会員IDごとの校閲履歴
- 各会員IDに紐づけて、過去に校閲した原稿・結果を保存・一覧・再表示。
- → **永続DBが必要**（Phase 1 までは不要）。

### ② 共有URLの発行（編集者 → チェック者 → ディレクター提出）
- 校閲後の原稿に対し、**閲覧用の共有URL**を発行して提出。
- ロール：編集者 / チェック者 / 最終チェック者（ディレクター）を想定。
- 実装：`shares` レコード（ランダムな公開トークン＝推測困難なURL、対象スナップショット、権限）を発行。

### ③ 共有URL上での「赤入れ」コメント（Word / Google ドキュメント風）
- ディレクターが**選択範囲にコメントを差し込み**、チェックバックを返す。
- 必要要素：
  - テキスト範囲のアンカー（開始/終了オフセット or 引用テキスト＋前後文脈で再特定）
  - コメントスレッド（本文・投稿者・日時・解決済みフラグ）
  - リアルタイム反映（あると望ましい）
- 文字単位ハイライトのロジックは既存 `content.js` / モックアップの資産が流用できる。

### DB / バックエンド方針（無料枠前提）
大前提は**無料の範囲**。Phase 1 は DB 不要で進める。Phase 2+ で導入する。

| 候補 | 内容 | 無料枠 | 評価 |
|------|------|--------|------|
| **Supabase**（推奨） | Postgres + 認証 + RLS + Realtime + Storage の統合 | 無料枠あり（DB 500MB等） | ◎ 認証・履歴・共有・コメント・リアルタイムを**1つで賄える**。③のリアルタイムにも有利 |
| Turso | SQLite(libSQL) ホスティング。DBのみ | 無料枠は寛大 | ○ 認証は別途（Auth.js）必要。軽量重視なら |

→ **②③（共有・コメント・ロール）まで見据えると認証とDBが密結合するため、Supabase に一本化する案を推奨。**
　これに伴い「3.認証」の第一候補も **Auth.js+Postgres → Supabase Auth（招待制）** に更新（無料枠・統合性で優位）。
　※アカウント未作成 → Phase 3 着手時に作成をサポートする。
- **Phase 1（いま）は DB もアカウントも一切不要**。クライアント完結でカウント＋校閲のみ。
